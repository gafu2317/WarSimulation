## このゲームの部品を作る際の案

ここからは公開資料の要約ではなく、この国家画面に対する妾の設計案。

| 部品 | 形・見た目 | 状態の伝え方 |
| --- | --- | --- |
| 時間操作 | 小さな色面、薄い輪郭。黒い台座を重ねない | 進行は緑、停止は赤。記号と文字も併用する |
| 決定ボタン | 面のある主操作。角・輪郭・厚みを一つの部品で揃える | ホバーは輪郭、押下は面の変化。無効時は理由を近くに表示する |
| 切り替えタブ | 隣接したまとまり。通常の決定ボタンとは輪郭を分ける | 選択中の面・下線を保持する。フォーカス移動と選択を混同しない |
| 施設の選択行 | 施設の絵かシルエット、施設名、レベルを一組にする | 選択中だけ面と印を強める。全行を強い箱で囲まない |
| 配分の行 | 施設、金額、スライダー、効果を近づけて並べる | 配分額を主役にし、最低額・上限は補足。効果と詳細操作も同じ領域にまとめる |
| 情報パネル | 静かな下地と見出し。必要な境界だけ線を使う | 情報そのものを決定ボタンに似せない |
| 資源表示 | 絵アイコンと数値を近づけ、名称は補助にする | 増加量・在庫・月の収入を表示形式でも区別する |

色はユーザー指定の「グレーにほんの少し紺」を基調にする。アクセント、明度差、細い輪郭、控えめな素材感を組み合わせる。材質を使う場合も、文字やアイコンより先に目立つ模様にはしない。

日本語フォントはプロジェクト指定を使い、見出し・数値・本文・補足のサイズと太さを揃える。絵に重なる左下メニューの文字と、管理画面の本文は用途が違うため、仕上げも分ける。

形の細さと入力範囲は別に扱う。タッチでも操作できる入力範囲を確保し、参考作の画面を小さい文字のまま模倣しない。今回の確認はUnity Editorで行い、実機確認は含めていない。

## AIが毎回別の部品を作らないための案

1. まず決定ボタン一つの見た目と状態見本を作る。通常、ホバー、押下、無効、キーボードのフォーカスを並べて確認できるようにする。
2. タブには選択状態と、選択＋フォーカスの組み合わせも用意する。操作ボタンの一時的な押下と区別する。
3. 固まった部品をPrefabとして登録する。各画面では部品ID、文言、アイコン、配置を指定し、色や輪郭を画面ごとに作り直さない。
4. 部品一覧には見本画像、用途、入力範囲、使える状態を記録する。新しい用途には、既存のどの部品を使うかを先に決める。
5. 画面の確認では文字のはみ出し、アイコンの縦横比、入力範囲、フォーカスと選択、スクロール時の固定領域を検証する。

調査時点では、共通の色定義、Builderの用途別生成、施設選択・配分・メンバーの共有Prefab、Editorの画面取得を使っていた。全ての操作を独立したPrefabにすることや、全状態を並べる専用カタログは未導入だった。現在使う部品と確認方法は [国家画面のUI](UI.md) を参照する。

## パネルの外形と素材感の試案（2026-10-25）

[当時の生成画像](../../Artifacts/CountryUI/PanelStyle-v1/facility-panel-concept.png) は過去の美術案として残す。Unityの実物や、再現を確認した部品の見本として扱わない。

- 見出しを本体から張り出す名札にし、外形に段差を付ける。
- 紺灰の細かい布地と薄い金属の縁を組み合わせ、角の接合部と弱い陰影で素材感を作る。
- 建設の内容に対応する薄い図面を余白へ入れる。本文や数値の背後は静かに保つ。
- 効果欄を折り返しのある差し込み帯として扱い、主パネルと同じ長方形を重ねるだけの見た目から変える。

### 現在の画面で確認したこと

[育成の実画面](../../Artifacts/CountryUI/MipMaps-v1/after/Training-AfterTabs-1280x720.png)と[配分の実画面](../../Artifacts/CountryUI/MipMaps-v1/after/Budget-1280x720.png)を目で確認し、[共通テーマ](../../Assets/Scripts/Country/CountryGovernmentTheme.cs)と[押下・無効状態の処理](../../Assets/Scripts/Country/CountryButtonFeedback.cs)を読んだ。画像は直前のMip Map確認時のものを使い、今回新たに画面を撮影したものではない。

- 紺灰の方向は共通しているが、下地・情報面・操作面の明度が近い。画像の黒い輪郭や金の枠が、面の違いより目立ちやすい。
- 金色が、選択中のタブ・兵士の輪郭に加え、日付、学校の説明、適用日、配分額、詳細リンクへ広く使われる。どれを優先して見るかが弱くなっている、というのが妾の見立て。
- 育成の訓練旗と配分の指令書は、形と材質で用途を区別できる。この違いまで一色へ揃える必要はない。
- 配分の残額には緑が使われている。残っている在庫と、今増えた量を同じ強調にするかは整理が必要。
- 無効ボタンは面の暗色化に加え、全体の透明度を45％へ下げる。実際の文字や素材の色は、テーマの値だけでは判断できない。

次は、不透明な共通色同士をsRGBから線形化して相対輝度で比較した結果。完成画面の測定値ではなく、色の組み合わせを見直すための予備確認である。Spriteの模様、Tintの乗算、透明度、文字の縁取りを含む最終表示の合否は判定していない。

| 比較する定義色 | 比率 | 読み取れること |
| --- | --- | --- |
| 下地 `#444F5D` とパネル `#53606F` | 1.30:1 | 面同士の明暗差は小さい。この数値だけで不合格とはしない |
| パネル `#53606F` と操作面 `#627080` | 1.27:1 | 面の色だけに操作の見分けを頼れない |
| 補足文字 `#AEB9C7` とパネル `#53606F` | 3.23:1 | 小さな重要文字として使う組み合わせは再検討する |
| 補足文字 `#AEB9C7` と操作面 `#627080` | 2.55:1 | 同じ補足色を、明るさの違う全ての面へ使い回さない |
| 本文 `#F1EEE5` と操作面 `#627080` | 4.36:1 | 本文色でも載せる面によって余裕が変わる |
| 濃紺文字 `#384351` と金の選択面 `#E0C894` | 6.15:1 | 明るい選択面に濃い文字を載せる現在の方向は活かせる |

### 本作へ提案する役割分担

美術の軸は「少し紺を含む灰色の土台、生成りの紙、落ち着いた金」。初期の色指定と現在の素材を踏まえた検討案で、具体的な色コードはまだ決定しない。画面全体を暗くする方針や、全面を紙へ置き換える方針は含まない。

「この色合いでわかりにくくならないか」という追加確認に対して、色の組み合わせは候補として使えるが、色名と役割だけでは視認性を保証できない、と整理する。前案では主操作の強さと、金の選択面・生成りの紙面の使い分けの定義が不足していた。選択面と紙面は位置や形も違うため、近い色であることだけで誤認すると断定はしない。

候補を具体化する際は、選択には金の輪郭や印、主操作には周囲と明確な明暗差のある面と読みやすい文字、副操作には控えめな面を使う。タブは金の面も使えるが、一般の情報パネルや装飾の枠を同じ強さにしない。明るい紙面では濃い文字、紺灰の面では明るい文字を使い、補足文字も背景に溶け込ませない。素材ごとの形・色の違いと、選択・決定の見分けを両立させる案である。

| 色・素材の役割 | 主な用途と使い方 |
| --- | --- |
| 紺灰の段階 | 下地・情報面・通常操作を整理する。隣り合う面の明度差と輪郭の強さを一緒に調整する |
| 生成り／濃紺の文字 | 紺灰の面では明るい文字、紙や明るい旗では濃い文字。補足も背景との組み合わせごとに用意する |
| 落ち着いた金 | 選択しているタブ・兵士・装備など、現在の対象を示す。一般の日付・説明・レベル表記を一律に金へしない |
| 緑 | 時間を進行する操作、増加量、完了。残高や残額は通常の数値色を基本にし、増減は `+` なども併記する |
| 赤系 | 時間を停止する操作、不足・危険・襲撃。操作と警告は記号・文言・位置で区別する。平常の「停止中」という状態説明まで常に警告色へしない |
| 紙・木・旗・物体の固有色 | 指令書、建設看板、訓練旗、資源や施設の絵。自然な素材色を保ち、操作状態は別の輪郭や印でも伝える |
| 国の識別色 | 地図の領有国を区別する。選択の金の輪郭とは役割を分け、国名や本拠地記号を併用する |

色を使う量も役割に合わせる。大きな下地は彩度を抑え、強い色は選択箇所や重要な合図へ絞る。小さな印は明確に、領土のような広い面は控えめにする。「必ず3色」「必ず60:30:10」といった固定比率は今回の採用基準にしない。

同じ色相を一用途だけに縛るものでもない。金貨が金色、封蝋が赤色であることは絵の内容を表す。選択枠や警告表示が表す操作上の意味とは区別する。金貨や封蝋を無意味に塗り替えず、装飾の赤が警告より強く目立つ場合は面積・彩度・位置を調整する。

主操作を全て緑や金の面へ揃える案は取らない。配分確定・訓練開始・建設決定は、それぞれの紙・旗・木のモチーフを保ち、読める文字、明確な押せる輪郭、周囲との明暗差で優先度を揃える。戻るなどの副操作は、それより控えめにする。

### 部品へ落とす際の状態ルール案

| 状態 | 本作での案 |
| --- | --- |
| 通常 | 素材と用途の色を保ち、文字と面の組み合わせを固定する |
| ホバー | 面や輪郭をわずかに変える。選択していないものまで金の選択面にしない |
| 押下 | 現在の沈み込みと面の変化を使う。新しい意味色を足さない |
| 選択中 | 金の面または輪郭と、選択の印を保持する。ホバーが外れても消さない |
| キーボードのフォーカス | 選択とは別の明るい輪郭で示す。選択中と同時に成立できるようにする |
| 使用不可 | 目立ち方と押下反応を抑える。操作名と、不足量・訓練中などの理由は読める明暗差を保つ |

実装に進む場合は既存の `CountryGovernmentTheme` と共通部品へ役割を集約する。AIが新しい画面を作る時も、既存の「下地」「明るい面の文字」「選択」「不足」などを指定し、部品ごとに色コードを増やさない。画像へ描く材質色と、実行時に重ねる状態色は別に管理する。

最初に調整する対象は、育成の実画面にある「タブ・兵士の選択行・訓練旗・補足文字」がよい。同じ画面で選択、主操作、補助情報を比較できるため。HD 1280×720と844×390で実際の表示を確認し、紙や木を含む他の面へ展開する。色だけでなく、面積・輪郭・文字の明度を一組で比べる。この確認や配色変更は今回まだ行っていない。

### 資料から得た考え方

経営ゲームでは、必要な情報を探し回る負担が戦略を考える時間を圧迫する。Anno 1800のUI担当者は、情報・操作・フィードバックを通じて、プレイヤーが戦略に集中できる構造を説明している。この国家UIでも、見つける・比べる・決める・結果を理解する、という一連の行動を評価の単位にする。[Anno 1800・DevBlog: User Interface](https://www.anno-union.com/devblog-user-interface-2/)

見た目の評価には、優先順位とまとまりも必要。明度・大きさ・文字の強弱・近接・余白によって読み順が変わる。軽く目を細めて見る方法も、大きな視覚的まとまりを探す補助になる。可読性そのものの検査とは分ける。[NN/G・Visual Hierarchy](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/)

候補や比較材料をその場で見られると、別画面の数字を覚えて戻る負担を減らせる。兵士・武器・施設を比較する際の画面往復を調べる根拠になる。[NN/G・Recognition and Recall](https://www.nngroup.com/articles/recognition-and-recall/)

情報を段階的に出す設計では、頻繁に必要な要点を最初から示し、専門的な情報を詳細へ置く。毎回必要な判断材料まで詳細に隠すと往復が増えるため、表示量だけでなく利用頻度を基準に分ける。[NN/G・Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)

ボタンの重要度を表すスタイルと、押下・フォーカス・操作不可・選択といった状態は別の設計事項。押した瞬間の反応と、結果として残る選択状態を区別して調べる。[NN/G・Button States](https://www.nngroup.com/articles/button-states-communicate-interaction/)

ゲーム全体での共通操作、現在地、ラベルと操作対象の対応、状態の説明も評価対象になる。重大な決定では確定前に内容を確認・修正できることが必要で、全ての小さな操作に確認を足す方針にはしない。[XAG 112・UI navigation](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/112)、[XAG 114・UI context](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/114)、[XAG 115・Error messages and destructive actions](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/115)

ゲームの世界観と部品の再利用も独立した評価対象にする。Anno 117の制作例は、控えめな材質、共通の形や装飾の組み合わせによって、全体のまとまりと場面ごとの個性を作っている。本作で装飾量を増やすことを決める資料ではなく、用途・材質・組み合わせの対応を考える参考にする。[Anno 117・UI visuals](https://www.anno-union.com/devblog-the-user-interface-team-and-a-deeper-dive-into-the-visuals/)

### 国家UIへ当てはめる10の観点

以下は上記資料と既存のゲーム仕様から組み立てた妾の提案。

| 観点 | 探す問題 | 国家UIで観察する問い |
| --- | --- | --- |
| 判断に必要な情報 | 数字はあるが、何を選ぶ根拠にすればよいか分からない | 学校の習得対象、兵士の既習得スキル、費用と増額効果を見て選べるか。比較するたびに別画面の数字を覚えて戻っていないか |
| 時間と確定状態 | 今の状態、編集中の案、適用後の状態を取り違える | 今月／来月、訓練予約／開始済み、詳細表示中の兵士／参加者を分けて理解できるか |
| 視覚的な優先順位 | 主操作や重要な変化が補足・装飾に埋もれる | 見出し、候補、判断材料、決定操作の順に目が移るか。枠・アイコン・選択色が全て同じ強さになっていないか |
| 情報のまとまりと余白 | 同じ判断に必要な情報が離れ、無関係な情報が一まとまりに見える | 費用・工期・効果、配分額・最低額・増額効果が対応付くか。頻繁に使う要点と詳細が適切に分かれるか。文字数だけでなく役割と材質に合う内側余白があるか |
| 操作の発見と予測 | 押せる部分や、押した後に起きることが分からない | 詳細表示・切替・確定・解除を見分けられるか。モチーフ付きの画像も操作できるものに見えるか |
| 反応と結果の理解 | 押下反応はあるが、登録・予約・精算が済んだか分からない | 押した直後の反応と、残る人数・状態・日付の変化を確認できるか。操作不可の理由と解決条件が分かるか |
| 毎月の操作負担 | 同じ入力や探索を繰り返す | 26人を探すスクロール、同じ説明の再表示、戻った後の位置の消失などで毎月手間が増えないか |
| 共通操作の学びやすさ | 画面ごとに同じ操作を覚え直す | 育成・遠征・防衛で追加／解除、詳細を開く、戻る、フォーカスの意味が共通か。画面の違いは役割から説明できるか |
| 実表示と入力 | 読める設定でも実際には読みづらい、狙いづらい | 実際の小画面・文字量で判読できるか。指で隣を押さないか。スクロールと選択が混ざらないか。重要な説明がマウスホバーだけになっていないか |
| 世界観とゲームとしての魅力 | 部品は揃っているが、用途や雰囲気が伝わらない | 指令書・旗・看板などの形が役割に合うか。繰り返す素材と場面の個性が両立するか。街・人物・操作より装飾が目立っていないか |

色の追加だけで各問題を解決しようとしない。文字の強弱、配置、輪郭、記号、状態名も合わせて調べる。可読性・色以外の手掛かりの根拠は [XAG 101](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/101)、[XAG 102](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/102)、[XAG 103](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/103)。タッチでのホバーの制約は [Microsoft・旧Windows設計資料](https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-mouse) を参照する。この旧資料は入力の制約だけを参考にし、Windowsの外観やWeb記事の文字サイズ・形状の具体値を、そのままゲームの基準値へ転用しない。

### 問題を見つける実施案

機能の存在に気付けるか、操作場所を見つけられるか、使えるかを順に調べる。最初からタブ名や押すボタンを教えると、発見や探索の問題が隠れるため、まず目的を渡し、必要な場合だけ手掛かりを足す。[NN/G・Stepped User Tasks](https://www.nngroup.com/articles/user-testing-stepped-tasks/)

本作での目的例：

- 次の遠征に必要な兵士を残しながら、誰を訓練に出すか決める。
- 国庫からお金を使わずに、育てたい施設への配分を増やす。
- 月途中に来月の予定を組み、いつ開始・完了するか説明する。
- 遠征メンバーと武器を組み、帰還予定と訓練予約の関係を説明する。

観察記録には、画面往復、探し直し、誤操作、説明を求めた箇所、実行結果の予想と実際の食い違いを残す。所要時間を測るときは情報探索・入力の時間と戦略を考える時間を区別し、速さだけで良し悪しを決めない。ゲームを初めて見る人と、操作を覚えた人の両方で調べる。

評価する状態は通常表示だけでなく、1日／2日以降、資金不足、満員、CP0・訓練・遠征中、長い説明、一覧の末尾、画面の再表示を含める。数値や効果が未確定の箇所では情報の理解と比較を調べ、戦略の正解を採点しない。

目視では全体の視線とまとまり、操作では判断・入力・状態変化を見る。自動検査は文字のあふれ、入力範囲、参照、状態保持などの補助に使う。世界観や魅力、判断しやすさの採用判定を数値検査だけに任せない。

### 改善候補の記録と優先順位

問題は「見にくい」だけで残さず、次の形にする。

`場面と条件 → 観察された迷い・誤認 → 判断や操作への影響 → 根拠画像・操作記録 → 対応する観点 → 修正後に確かめること`

優先順位は発生頻度、影響、繰り返し起こるかで判断する。[NN/G・Severity Ratings](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/)。深刻度と、直す手間は別に記録する。見た目の魅力・世界観もゲームの品質として評価に残す。

最初に調べる対象は、育成の判断材料、今月／翌月と選択案／確定済みの理解、26人の比較と毎月の操作負担を提案した。公開版17の操作検査では、習得する技の効果不足、予約の制限説明、比較時の探し直しなどを確認し、表示領域と状態色を含む12件の改善候補を[UXAudit-v1](../../Artifacts/CountryUI/UXAudit-v1/verification.md)へ記録した。改善効果や実利用者の迷いはまだ検証していない。現行の仕様・採用状態は [UI](UI.md)、[月初の政務UI](月初の政務UI.md)、[入口](README.md) を基準にする。
