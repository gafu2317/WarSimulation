# 診断ログ

関連: [README](README.md) · [判断の流れ](判断の流れ.md) · [自動戦闘デバッグ](自動戦闘デバッグ.md)

開発エージェントがバトル後にAIの判断を診断するための、開発専用イベントログの説明。

## 目的

- 各AI判断の計画と実行結果、およびバトル中の重要な変化点をテキストファイルへ記録する
- 後から `rg` / `Read` で「なぜ魔石ではなく敵を攻撃したか」などを追えるようにする
- ゲーム内AIのランタイム判断には影響しない（開発ツール）

## 出力先

```text
Logs/CombatBattles/battle_yyyyMMdd_HHmmss_fff.log
```

プロジェクトルート直下。`.gitignore` で Git 管理対象外。

戦闘開始時・終了時に Console へファイル名を出す。古いファイルは既定で直近 50 件まで残し、超えた分は作成時に削除する（Inspector の `Max Retained Log Files`）。

## 有効化

- Unity Editor または Development Build のみ
- シーンに [`CombatBattleEventLogger`](../../Assets/Scripts/Combat/Debug/CombatBattleEventLogger.cs) を配置
- Inspector の `Enabled` をオン（デフォルトオン）
- `CombatBattleFlow` が `Running` になったタイミングで自動的に新規ログファイルを作成

## ログ形式

出力は1バトル1ファイルの通常テキストで、イベント名と `key=value` を同じ行に置く。JSONLや別の詳細ログは作らない。

### ヘッダ

`BATTLE_START` より前に、次の戦闘メタデータを記録する。

| 項目 | 内容 |
|---|---|
| `file` | ログファイルの絶対パス |
| `map` | マップ名 |
| `seed` | 戦闘に使用したシード |
| `stonePositionsReversed` | 魔石配置反転の有無 |
| `weather` | 天候 |
| `timeScale` | 戦闘開始時の TimeScale |
| `fixedDeltaTime` | 戦闘開始時の FixedDeltaTime |
| `preserveFixedDeltaTime` | 自動戦闘設定。通常戦闘は `n/a` |
| `unityVersion` | Unity バージョン |
| `playerBuildGuid` | Player ビルド GUID |
| `participants` | 参加キャラごとのチーム、武器、性格 |

### イベント

| 行頭 | 意味 |
|---|---|
| `# CombatBattleLog` | ファイルヘッダ |
| `BATTLE_START` | バトル開始 |
| `AI_PLAN` | 初回または意味のある変更後の計画。`planId` と `decisionTick` で実行と相関できる |
| `AI_PLAN_REPEAT` | 同一計画を抑制した回数、継続時間、目的地更新回数、最終目的地 |
| `AI_EXECUTE` | 移動開始、スキル開始、実行失敗。何も開始せず失敗理由もない行は出さない |
| `AI_CANCELLED` | 撃破または戦闘終了で実行されなかった Prepare 済み計画 |
| `OBJECTIVE` | AI目的の切替（理由コード付き） |
| `SKILL` | 成功した非通常攻撃（バフ、回復、大技など） |
| `SKILL_RESULT` | `NoEffect`、`Failed`、`Cancelled` のスキル結果 |
| `SNAPSHOT` | 魔石HP・生存数（デフォルト10秒間隔） |
| `DEFEATED` | 撃破（戦闘離脱） |
| `STONE_TARGET` | 魔石ダメージの実行者、魔石ID、ダメージ量、ActionId、DecisionTick |
| `STONE_DESTROYED` | 主魔石破壊 |
| `BATTLE_END` | 通常終了または timeout のバトル終了サマリ + 通常攻撃集計 |
| `BATTLE_ABORTED` | Logger無効化、シーン破棄、アプリ終了などによる中断 |

通常攻撃（斬撃・盾撃・魔弾・通常攻撃）の成功は1行ずつ書かず、`BATTLE_END` の `skillTally` に集計される。通常攻撃を含む失敗・無効果・キャンセルは `SKILL_RESULT` に残る。

## AI計画の読み方

`AI_PLAN` は同じキャラの計画が初めて現れた時と、次の意味的な項目が変わった時だけ出力する。

- 目的
- 行動コード
- 移動対象の種類
- 対象キャラまたは進攻ルートID
- スキルID
- スキル対象キャラ、対象魔石、対象地点

移動座標の小さな変化だけなら同一計画として抑制される。後続の `AI_PLAN_REPEAT` は、その計画が何回繰り返されたか（`count`）、最初の計画からの継続時間（`duration`）、目的地の更新回数（`destinationUpdates`）、最後に記録した目的地（`lastDestination`）を示す。計画が切り替わる時、または戦闘が終わる時に出力される。

特定キャラの計画と実行を見る:

```bash
rg "AI_PLAN actor=Char_Wand01|AI_EXECUTE actor=Char_Wand01|AI_CANCELLED actor=Char_Wand01" Logs/CombatBattles/battle_*.log
```

目的の切替を見る:

```bash
rg -- "-> 敵魔石を破壊" Logs/CombatBattles/
```

バトル結果と中断を見る:

```bash
rg "BATTLE_END|BATTLE_ABORTED" Logs/CombatBattles/
```

スキルの無効果・失敗・キャンセルを見る:

```bash
rg "SKILL_RESULT outcome=(NoEffect|Failed|Cancelled)" Logs/CombatBattles/
```

## 実装の要点

- イベント源: [`CombatAiDecisionEvents`](../../Assets/Scripts/Combat/Characters/AI/CombatAiDecisionEvents.cs), [`CombatSkillActionEvents`](../../Assets/Scripts/Combat/Skills/CombatSkillActionEvents.cs), [`CombatHealth.Defeated`](../../Assets/Scripts/Combat/Characters/CombatHealth.cs), [`CombatMagicStoneSystem.MainStoneDestroyed`](../../Assets/Scripts/Combat/Systems/CombatMagicStoneSystem.cs)
- 整形: [`CombatBattleLogFormatter`](../../Assets/Scripts/Combat/Debug/CombatBattleLogFormatter.cs)
- `planId` はロガー内の計画ID、`decisionTick` は既存のAI判断tick。スキル行では既存の `ActionId` と `DecisionTick` を使う
- `OBJECTIVE` は目的変更時だけ記録し、`AI_PLAN` との役割を重複させない
- `AI_EXECUTE` は開始または失敗が観測できる時だけ記録する
- `CombatSkillActionEvents.Cancelled` も購読し、成功と誤解されない `SKILL_RESULT` にする
- `STONE_TARGET` と視界診断はファイルへ一度だけ書き、カメラ位置・回転、Orbit設定、Editor設定は通常ログに含めない
- 行ごとの Flush は行わず、開始、定期 `SNAPSHOT`、終了、中断時に Flush する

## 終了経路

- 勝利・敗北: `BATTLE_END outcome=Victory` または `Defeat`
- timeout: `BATTLE_END outcome=Timeout`
- Logger無効化、シーン破棄、アプリ終了、戦闘状態のリセット: `BATTLE_ABORTED reason=...`
- 戦闘終了後に残った Prepare 済み計画: `AI_CANCELLED reason=BattleEnded`
- 撃破済みキャラに残った計画: `AI_CANCELLED reason=ActorDefeated`

## 肥大化防止

- 旧指標値や候補順位のダンプは行わない
- 高頻度の同一計画と通常攻撃成功は集約する
- 1バトル1ファイル
- 本番ビルド非搭載
- 自動戦闘の候補順位、判断間隔、TimeScale評価方法は変更しない

通常ログで残す情報を増やす場合は、AIの判断・実行・結果の相関に必要かを先に確認する。カメラやEditorの状態は、戦闘判断の説明に必要な別の再現調査で扱う。
