# 5人編成・全マップ探索

## 目的

5人の味方編成を総当たりし、次を同時に調べる。

- 全20条件（10マップ × 魔石配置の通常・反転）を通した強い編成
- 各編成がどのマップで強いか
- 通常配置と反転配置で成績が変わるか

Editor Play は使わない。軽量な Standalone Player をマップ単位で起動し、外部ランチャーから並列実行する。

## 現在の探索条件

| 項目 | 値 |
|---|---:|
| 編成人数 | 5人固定 |
| 合法な編成候補 | 6,993 |
| マップ | `AuthoredMap`, `AuthoredMap 1`〜`AuthoredMap 9` |
| 配置 | 通常・反転 |
| 1候補あたりの条件数 | 20 |
| 時間倍率 | 16倍 |
| 1試合のゲーム内タイムアウト | 1,200秒（20分） |
| 外部Player並列数 | 5 |
| Player内 Job Worker数 | 1 |
| 敵編成 | Neutral 5人（Sword×2, Shield, Wand, Rosary） |

`AuthoredMap 10` は未完成のため対象外。総当たりを1シードで完走すると `6,993 × 20 = 139,860` 試合になる。

## 方式

1. `CombatCompositionSweepGenerator` が5人の合法編成を重複なく列挙する。
2. Pythonランチャーが探索設定を10マップに分割する。
3. 軽量Playerを最大5プロセス起動し、空いた枠へ次のマップを投入する。
4. 各Playerは同じ候補・同じ基準シードで通常配置と反転配置を評価する。
5. ランチャーが10個のレポートを候補キーで結合し、総合・マップ別・配置別の結果を1つにする。

候補キーは役割の並び順に依存しない。通常・反転では共通シードを使うため、配置差を比較しやすい。

## 初回準備と設定更新

Unityで `Assets/Scenes/GafuTest.unity` を開き、Play Modeを停止した状態で次を実行する。

1. `Tools > War Simulation > Auto Battle > Setup Current Scene`
2. Consoleで、有効な10マップを設定した旨のログを確認
3. `Tools > War Simulation > Auto Battle > Build Lightweight Player`

Setupは既存対象を検証してから、専用ルート `CombatAutoBattleRuntime` だけを作り直してシーンを保存する。軽量ビルドの出力は `.unity/CombatAutoBattleLight/CombatAutoBattleLight.app`。

コードやシーン設定を変えた場合は、必要に応じてSetupと軽量ビルドをやり直す。

## 回し方

プロジェクトルートで実行する。

### 1候補で疎通確認

```bash
python3 Tools/AutoBattle/parallel_sweep.py \
  --template Tools/AutoBattle/five-member-map-smoke.json \
  --worker-count 1
```

10マップの通常・反転、合計20試合が完了してから全探索へ進む。

### 全候補を5並列で探索

```bash
python3 Tools/AutoBattle/parallel_sweep.py \
  --template Tools/AutoBattle/five-member-map-sweep.json
```

`--worker-count 5 --job-worker-count 1` が既定なので省略できる。負荷をさらに下げるときだけ `--worker-count` を減らす。

### 既知の強候補を20条件で再検証

全候補探索は長時間になるため、過去の試行で勝率が高かった候補だけを現行Playerで確認する場合は次を使う。

```bash
python3 Tools/AutoBattle/parallel_sweep.py \
  --template Tools/AutoBattle/five-member-map-shortlist.json
```

これは全6,993候補の順位を確定するものではなく、候補絞り込み後のマップ適性・通常/反転差を確認する再検証である。

### 1万試合以上の統計検証

候補絞り込み後の4編成を各20条件・各125シードで回すと、`4 × 20 × 125 = 10,000`試合になる。20分制限で実行する設定は次の通り。

```bash
python3 Tools/AutoBattle/parallel_sweep.py \
  --template Tools/AutoBattle/five-member-map-statistical.json
```

これは候補選択の探索と、選択後の統計評価を分離する方式である。全6,993候補の総当たりを統計評価まで同時に行う設定ではない。

### 並列数を再計測

```bash
python3 Tools/AutoBattle/parallel_sweep.py \
  --template Tools/AutoBattle/five-member-map-smoke.json \
  --benchmark-worker-counts 1 5 10
```

前回の1候補ベンチマークでは、Job Worker 1の5並列が1並列比で約4.1倍、10並列が約5.8倍だった。負荷と伸びの釣り合いから通常運用を5並列にする。

## 分割して回す

設定JSONの `CandidateOffset` と `CandidateLimit` で候補範囲を分割できる。

```json
{
  "CandidateOffset": 0,
  "CandidateLimit": 100
}
```

`CandidateLimit: 0` は残り全件。異なる範囲を回した結果はランチャー単体では再統合しないため、通常は1回の全探索を使う。

## 主な設定

| キー | 意味 |
|---|---|
| `EnumerateAllCandidates` | ランダム抽出ではなく合法編成を全列挙 |
| `EvaluateBothStonePositions` | 通常・反転を両方実行 |
| `UseCommonSeeds` | 候補・配置間で基準シードを共有 |
| `DisableDiagnostics` | 大量探索では試合ごとの診断ログを停止 |
| `MatchesPerCandidate` | 各マップ・各配置で繰り返す試合数 |
| `BaseSeed` | 乱数の基準値 |
| `CandidateOffset` / `CandidateLimit` | 候補範囲 |
| `TimeoutSeconds` | 1試合のゲーム内制限時間。現在1,200秒 |
| `TimeScale` | Player内の時間倍率。現在16倍 |

## 結果の場所と読み方

結果は `Logs/AutoBattleParallel/<timestamp>/workers_5/` に出る。

| 出力 | 内容 |
|---|---|
| `summary.json` | 全マップを統合したランキング、速度、マップ別所要時間 |
| `benchmark.json` | 指定した並列数ごとの速度比較 |
| `<map>/config.json` | そのPlayerへ渡した設定 |
| `<map>/player.log` | Unity Playerログ |
| `<map>/AutoBattles/sweep_*.json` | マップ単体の探索結果 |

`summary.json` の `Ranking` は `WinRate` 降順。各候補には次が入る。

- `Maps`: 通常・反転を合計したマップ別成績
- `Scenarios`: マップ × `StonePositionsReversed` の成績
- `Timeouts`: 勝敗がつかず1,200秒に達した試合数

総合順位だけでなく、`Maps` と `Scenarios` を見て得意マップと配置依存を確認する。タイムアウト率が高い編成は、単純な敗北と区別して扱う。

考察資料は、探索完了後に次で生成する。

```bash
python3 Tools/AutoBattle/analyze_sweep.py \
  --summary Logs/AutoBattleParallel/<timestamp>/workers_5/summary.json \
  --output Logs/AutoBattleParallel/<timestamp>/analysis.md
```

上位20編成、マップ別傾向、通常・反転の成績、timeout率をMarkdownへまとめる。元の`summary.json`を残したまま、順位と考察を共有できる。

## 注意点

- 5並列でも、同じ候補・シードの単一試合結果が1並列時と完全一致しないことがある。AI判断と物理更新がフレーム負荷の影響を受けるため、現状の結果は統計的な評価として使い、1試合だけを完全再現の根拠にしない。
- 比較の信頼度を上げる場合は `MatchesPerCandidate` を増やすか、`BaseSeed` を変えて複数回評価する。必要な回数は求める精度に基づいて決める。
- 現在の全探索は途中候補を統計的に打ち切る方式ではない。6,993候補を全20条件で評価するため、最初は必ずsmoke設定で疎通を確認する。
- 1,200秒はゲーム内時間であり、16倍速なら理論上75秒相当だが、実時間はCPU負荷・フレーム進行・試合終了の早さで変わる。
- macOS環境では、5並列のPlayer同時起動時に全プロセスが終了コード`-6`（`NSMenuBarPresentationInstance`内のabort）で停止する事象を確認した。`summary.json`と10マップ分の`sweep_*.json`が揃わない実行は結果として扱わず、まずsmokeを`--worker-count 1`で実行してから統計実行へ進む。
- 大量探索では `DisableDiagnostics: true` を維持する。AI判断を詳しく調べる個別再現だけDevelopment Buildと診断ログを使う。
- Player実行中に同じシーンや戦闘データを編集しても、そのPlayerには反映されない。変更後は軽量Playerを再ビルドする。
- ランチャーを停止すると実行中Playerも終了するとは限らない。再実行前に残留Playerがないことを確認する。

単一編成の詳細調査と診断ログについては[自動戦闘デバッグ](自動戦闘デバッグ.md)を参照する。
