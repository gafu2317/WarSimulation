# 街の素材管理とUnityへの移行

## 今回の準備範囲

既存の素材を削除・再生成せず、街づくりに使用する原本、制作スクリプトの依存関係、整理候補、Unityに渡すための作業を明確にする。

確認条件は、採用候補のコレクションが実際の `.blend` に存在すること、削除してはいけない依存ファイルを区別できること、未実施のUnity移行作業を明記すること。今回は取り込み前の棚卸しと手順整備であり、FBX書き出し・マテリアル移植・Prefab化の完了を意味しない。

## 普段見る場所

| 場所 | 内容 | 扱い |
|---|---|---|
| `ArtSource/Blender/` | 編集可能な `.blend` 原本 | 残す。Blenderでの手修正もここに保存する |
| `Tools/Blender/` | 生成・検証・修正のPython | 残す。ゲーム実行時には不要 |
| `docs/Art/` | 見本画像・寸法・検証結果 | 制作確認用。Unityへ入れない |
| `Assets/Models/` | Unityが読み込むモデル | `.meta` とセットで管理する |
| `Assets/Prefabs/` | Unityで配置するひな形 | 街づくりでは通常こちらを配置する |

現状ですでに制作データは `Assets` の外に分かれている。大量に移動するより、この区分を維持して入口を整理する方が安全。`Assets` 外のPythonや確認画像は、通常のUnityアセット取り込みの対象ではない。

`.blend` は完成した模型、Pythonは模型を作るレシピに相当する。Pythonを消しても保存済みの模型自体は消えないが、再生成やまとめて変更する手段を失う。また、Blenderで手修正した内容が自動的にPythonに戻るわけではない。取り込み時は保存済み原本から書き出し、原本を生成スクリプトで上書きしない。

## 削除・保管の判断

2026-09-01の調査値。容量はMiB相当で、ディスクの割当容量とは異なる。

| ファイル | 現状 | 判断 |
|---|---:|---|
| `Tools/Blender/*.py` | 22本、約0.30MiB | 残す。古い名前のファイルも新作から参照される |
| `Tools/Blender/__pycache__/*.pyc` | 4個、約0.14MiB | 再生成可能なキャッシュ。整理候補。ただし現在Git管理されている |
| `ArtSource/Blender/**/*.blend1` | 9個、約5.27MiB | 自動バックアップ。現行原本の正常性と復旧用バックアップを確かめてから整理する |
| `docs/Art/**/*.png` | 47枚、約134.40MiB | 容量の主因。代表画像は残し、不要と決めた比較画像だけ保管先へ移す候補 |
| `docs/Art/**/model_manifest.json` / `validation.json` | 小容量 | 素材名・寸法・検証記録として残す |
| `KingdomBuildings.blend` | 初期のデフォルメ版 | 比較用の旧案として残す。対応Pythonは現行版から参照される |
| `FantasyEntertainmentDistrict.blend` | 以前の街区案 | 今回の主採用から外すだけで、不要と決めつけて削除しない |
| `GroundedRockReview/` / `TrimmedRockReview/` | 岩の接地修正の比較と出力 | Unity側で採用した岩との対応を確認するまで保留。`Review`という名前だけで削除しない |

この準備では削除や移動は行っていない。キャッシュのGit追跡を外す場合、`.gitignore` を追記するだけでは既存の追跡は解除されないため、別途追跡解除が必要。

`Assets` 内の `.meta` はゴミではない。参照を維持するIDが入っているため、単独で削除しない。素材を移動する場合はUnityのProjectウィンドウを使うか、対応する `.meta` も一緒に移動する。[Unity公式資料](https://docs.unity3d.com/ja/current/Manual/AssetMetadata.html)

`Library`、`Temp`、`obj`、ログなどの生成物は原本と区別するが、今回の棚卸しは街の制作ファイルに限定した。容量確保のためのプロジェクト全体の削除は行わない。特に `Assets`、`Packages`、`ProjectSettings` は一括削除しない。

## Unityで配置可能にする作業

対象プロジェクトはUnity **6000.4.3f1 / URP 17.4.0**。`ProjectSettings/ProjectVersion.txt` と `Packages/manifest.json` を確認した。

1. **代表的な一区画で取り込み方法を確かめる。** 民家・直線道路・露店・街灯で、形状、上方向、正面、寸法、接地、色を確認する。その後、同じ方式で採用素材に展開する。
2. **保存済み原本から素材単位でFBXへ書き出す。** 原点・名前・寸法を保ち、プレビューの床・照明・カメラは含めない。Blender Z-upとUnity Y-upの変換は書き出し／取り込みで一度だけ行い、Unityで寸法を照合する。
3. **質感をUnity用に移す。** 現在の原本はNoiseやBrickなどのBlenderノードを使う。石畳・石積みの模様はポリゴンで刻まれているとは限らず、FBXだけでは同じ見た目を保証できない。模様を保持する部分はUVを用意して色・法線などをテクスチャへベイクするか、URP側で対応するマテリアルを作る。単色で十分な部分は共通マテリアルにまとめる。形状にUVがない部品もあるため、全素材がそのままベイク可能とは扱わない。
4. **Prefab化する。** 「配置用の親 → 表示モデル」を基本に、通常の小物は接地点を親の原点にする。原本の編集しやすさを保ち、Unity向け出力だけで固定部品の結合を検討する。モデル更新時もPrefabの参照を維持する。
5. **配置用の確認シーンを作る。** 本番シーンを変更せず、カメラ・ライト・基準寸法を置き、道路の接続と建物の大きさを確認する。通常のプレイ距離とズーム時の両方で見る。

道路は8mピッチ、車道の基準高さはUnity Y=0、歩道はY=0.12。道路の厚みは地面より下にあるため、メッシュの最下点を無条件にY=0へ持ち上げない。木柵・木門は始点基準で4mピッチ。全素材を同じ中心原点に変更すると接続の基準が壊れる。

衝突判定・通行可能領域・NavMeshは、街でキャラクターがどう移動するかに応じて設定する。門や中庭を大きなBoxColliderでまとめて塞がない。今回の準備段階では戦闘用のレイヤーやNavMesh設定を流用しない。

Blenderファイルを直接 `Assets` に置く方法もあるが、Unityによる変換時にBlenderが必要になるため、このプロジェクトでは原本を外に残して明示的にFBXを渡す運用を推奨する。[Unity公式資料](https://docs.unity3d.com/ja/current/Manual/HOWTO-ImportObjectsFrom3DApps.html)
